# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## OnGarage monorepo

Four Expo (SDK 57, React Native 0.86, React 19.2, TypeScript) apps that are the sides of one marketplace, plus the code they share. npm workspaces; one `node_modules` and one `package-lock.json` at the root.

```
apps/user       vehicle-owner app (SOS, post repair jobs, receive bids, direct bookings, workshop jobs, activity, OnMart parts marketplace, profile)
apps/garage     garage-owner app (SOS inbox + 10-step dispatch, job feed + bidding, schedule/workshop jobs, OnMart (marketplace, job parts, referrals), garage profile)
apps/parts      OnMart Shop, the parts shop's back office (garage requests + customer enquiries + open wall, orders + dispatch / counter pickup, stock, referrals, shop profile)
apps/tech       technician app (duty check-in, SOS field steps, workshop job cards, parts pickups, garages + rates, earnings)
packages/shared @ongarage/shared — types (the backend contract), theme engine + palettes, fonts, glass UI kit, line icons,
                BottomNav, Sheet, NoticeToast, SwipeCard, GarageCard, LevelBadge, CloseCode, workshop sheets, GoogleMap +
                maps helpers, service categories, formatting, marketplace rules (src/marketplace) and the AI decisions
                layer (src/ai); unit tests in test/
e2e/            browser tests for all four apps (specs/), run against the dev servers
```

There is no backend yet: every app runs on seed data and **simulates the other apps** (see below). The types in `packages/shared/src/types.ts` are meant to become the backend contract. Planned next: an admin app for OnGarage staff, then the backend, a Claude-backed AI provider, and Laya.

## Commands (run from the repo root)

```bash
npm install            # installs every workspace
npm run user           # owner app dev server,      port 8091 (npm run user:web for web)
npm run garage         # garage app dev server,     port 8092 (npm run garage:web)
npm run parts          # parts shop app dev server, port 8093 (npm run parts:web)
npm run tech           # technician app dev server, port 8094 (npm run tech:web)
npm run typecheck      # tsc --noEmit in every workspace (there is no linter; this is the check)
npm test                                        # unit tests: shared rules + AI layer
npm test -- workshop                            # only test files whose name contains "workshop"
npm test -- --test-name-pattern="grace period"  # only matching tests
npm run e2e            # browser tests against the four running dev servers
npm run e2e -- owner   # only specs whose file name contains "owner"
```

Each app's port is fixed in its `package.json` scripts, so all four run at once with no extra flags; keep ports unique when adding an app. Add a dependency to one app with `npm install <pkg> -w @ongarage/user` (keep versions identical across apps so React/React Native are hoisted once). Clear Metro's cache with `-- --clear` after moving files between packages. On this Windows machine Node sometimes segfaults (exit 139) at start-up, in `npm`, `tsc` and `expo start`: just run the command again (a `for` loop that retries `npx expo start --port <p>` works), and start the four dev servers one after another, not at the same time (started together they hang before Metro is up). Installing packages can stop a running Metro server — restart it before `npm run e2e`.

## How each app is built

- **No navigation library.** `src/app/_layout.tsx` (Expo Router) just renders `src/App.tsx`, which holds the bottom-tab state (`BottomNav` from shared, tabs in `src/constants/tabs.ts`) and opens full-screen flows as `<Modal>`s. Details views and forms are sheets (the shared `Sheet`) or cross-dissolve modals.
- **Stores are React contexts in `src/context`** (owner: `BidsContext`, `BookingsContext`, `WorkshopContext`, `NoticeContext`, …; garage: `GarageContext` + `PartsContext`; parts: `ShopContext`; tech: `TechContext`). They hold the seed data from `src/constants/mockData.ts` and simulate the other sides with timers: a `live` ref gives callbacks the latest state, `later(fn, ms)` schedules a simulated reply (cleared on unmount), and `notify()` shows a `NoticeToast`. Each app wraps the shared `Sheet` and `NoticeToast` in its own `components/Sheet.tsx` / `components/Toast.tsx` so toasts appear above open sheets and modals.
- **Seed data is shared by name across apps** so the simulations line up: the garage app is "TOPCODE Tuning & Service", the parts app is shop "Galle Auto Parts" (ps1), the technician app's user is "කසුන් ජයසිංහ" (garage `TEAM` m2). Refer to seeded entities by id, never by array position. `apps/user/CLAUDE.md` has owner-app specifics.

## Marketplace flows and rules

Every owner flow has a garage counterpart: SOS request → accept/quote → assign mechanic + live location → arrived → repairing → complete → scan the owner's QR; posted job → bid (price, warranty, est. time) → booking (a bid wins in the simulation when it is ≤ 1.05 × `marketPrice`); direct booking from a service category → garage confirms the slot, proposes another time or declines within 2 h (doorstep: garage goes to the owner; otherwise the owner gets the garage's location and phone); garage profile = the `GarageCard` owners see. When changing a flow, change both sides' simulations so they stay consistent.

**Marketplace rules** live in `packages/shared/src/marketplace` so every app computes trust scores, levels, intake limits, plans, guarantee splits and workshop bills the same way; change them there (and their tests), not in an app.

**Workshop job rule:** every booked repair (won bid or confirmed direct booking) follows the shared `WorkshopProgress` (`marketplace/workshop.ts`): booked → vehicle received with condition photos → diagnosis report (findings, photos, part and labour lines) → the owner approves all, some or none of the lines → repairing → ready for handover (checklist, before/after photos, old parts kept, bill) → closed only with the owner's QR or 6-digit code (`CloseCode` / `CloseJobSheet`) → warranty. Work found mid-repair goes to the owner as an `ExtraWorkRequest` (`DiagnosisSheet` with `extra`); the owner approves it line by line (`decideExtra` in the owner app) and handover waits until they answer (`pendingExtra`). Technician diagnoses go straight to the owner — no manager review (most Sri Lankan workshops have no separate manager). **Owner not answering extra work:** a technician's hands are busy, so the garage or technician can call the owner and record the answer with `ExtraByPhoneSheet` (`decideExtraByPhone`: tick the approved lines, no confirm code, `decision.via = 'phone'`, shown to the owner in the tracker); if the owner can't be reached they either wait (`ExtraWorkRequest.waitingSince`, `ownerWaiting`: free — `OWNER_WAIT_FEE` = 0, and `ownerWaitMs` is left out of delay measures) or put the extra work aside (`deferExtra`, `via = 'deferred'`: nothing billed or ordered) and finish the agreed work. Handover still waits while an extra is neither answered nor deferred. **Chat:** the owner and the garage can write to each other about a booked job (a direct booking or a won bid), from the 💬 button on the job card (`ChatSheet`, `ChatIconButton`, `useChatStore` in `packages/shared/src/ui/chat`; rules in `marketplace/chat.ts`, tested in `chat.test.cjs`). The thread is the job's id, each app has a `ChatContext` that opens the sheet and shows unread counts, a message that moves the deal off the app (a phone number, paying elsewhere) is held back like in OnMart, there is always a call button, and the other side's replies are simulated until there is a backend. In the garage app the chat icon in the top header opens an inbox of every conversation (a customer's direct request, a won bid, an accepted SOS; `ChatInboxSheet`), and a job keeps one thread from the request to the booking (`chatKey` drops the booking's "b-"). **Calls:** the garage / technician and the owner can ring each other at any time during a job, with no request or permission step — the garage and technician apps have a call button, and the owner's repair cards have a 📞 icon (`CallIconButton`) beside the garage name. Labour (agreed price + approved labour lines) and parts are billed separately (`workshopBill`). Stopping at the diagnosis costs only `INSPECTION_FEE`. A problem at handover goes to the garage for rework first, then can be escalated to OnGarage; a warranty claim is answered by the garage. The four sheets (`CheckInSheet`, `DiagnosisSheet`, `HandoverSheet`, `CloseJobSheet`) are shared by the garage app (`BookingActions`, `WorkshopPanel`) and the technician app (`WorkshopJobSheet`); the owner side is `WorkshopContext` + `components/workshop` in `apps/user`. Simulations: the garage and technician apps have the owner approve every line after a few seconds; the garage app's battery booking comes back once with a problem; the owner app simulates the garage receiving, diagnosing, asking for extra work once on the seeded brake job, reworking and scanning. Part prices come from the shared `partMarketPrice` table that the garage, technician and parts shop apps all use.

**Spare parts rule:** a garage orders parts for a booked job from nearby parts shops (Parts tab, `PartsContext`; contract types `PartsRequest` / `PartQuote` / `PartsOrder`). Shops may only quote the part type the owner chose; when the owner chose Genuine and none is available, Recon needs the owner's approval first. Parts are billed to the owner separately from the garage's labour (`Booking.partsCost`). **When:** for a workshop job, parts are ordered only for lines the owner approved (diagnosis or extra work), or before the diagnosis only for parts the owner named in their post (AI `classifyJob` → `partsMentioned`); `PartsContext.toOrderFor` gives exactly those lines, the request records them in `forLineIds`, and handover is blocked while approved parts are unordered or undelivered. **Pickup:** every quote may carry `pickup` (counter collection, parts price only); the garage chooses delivery or pickup and who collects (the garage, or a team member — one with the technician app gets a `PartsCollectTask`). A pickup order goes confirming → ready (held at the counter with a 6-digit `pickupCode`, QR payload `pickupCodePayload`) → collected; the shop checks the code with the shared `CloseJobSheet` before handing over. In the garage app `PartsContext` simulates the shops (`constants/parts.ts`); `apps/parts` (`ShopContext`) uses the same types. TOPCODE's brake-pad order is collected from the counter by its technician in both the parts app and the technician app.

**OnMart rule (spare-parts marketplace):** one marketplace across the owner app (OnMart tab), the garage app (OnMart tab: Mart / Job parts / Referrals; the old Parts tab is now "Job parts") and the parts app ("OnMart Shop", the shop's back office). Rules live in `packages/shared/src/marketplace/partsMart.ts` (search ladder `SEARCH_RINGS` 10 km, then 50 km, then nationwide; `wallVisibleTo`, `rankShops`, `shopServiceScore`, `fitmentLevel`, `priceTag`, `canonicalPartName`) and `referral.ts`; the shop directory, published stock, trade agreements and service kits are `constants/martShops.ts` and `serviceKits.ts` (shops are shared by id and name: ps1 = "Galle Auto Parts", the parts app's own shop). **The garage app's Mart segment is the owner app's OnMart** (same screens and flows, copied into `apps/garage`: `screens/MartScreen`, `components/mart`, `context/MartContext` and `WallContext`), buying for the garage; its buyer hooks (`useUserLocation`, `useVehicles` = the vehicles on its open jobs, `useNotice`, `useProfile`, `useWorkshops`) are small adapters in `apps/garage/src/context`, and the owner-only parts (parts the customer buys for a job, referral disclosures) are left out. Change the owner OnMart and its garage copy together. **Buyer flow:** ask nearby shops (or one shop), or post on the open wall (`MartAudience` shops / wall / both; the wall reaches only shops that sell that part type and never shows the poster's phone) → shops answer with a `ShopOffer` → reserve (the shop holds it; a 6-digit purchase code, QR payload `purchaseCodePayload`) → collect, inspect and pay at the counter, or delivery (inspect at the door) → warranty card, 7-day return, rating only for a verified purchase. Payment is never in the app. Shop rankings never use referral fees (tested). **Customer buys it:** a diagnosis or extra-work line with `source: 'owner'` (plus `partNo`, `recommendedShopIds`) is not ordered by the garage and not on its bill (`linesOwnerBuys`, `ownerPartsPending`, `workshopBill().ownerParts`); handover waits for a shop-verified purchase; the garage's recommendations become `PartReferral`s. **Referrals:** statuses only move forward (recommended, viewed, reserved, purchased, fitted); commission (the shop's %, default 3, cap `COMMISSION_CAP_PERCENT` = 5) is tracked, never added to the owner's price, disclosed to the owner (`referralDisclosure`), earned only when the part was fitted and the job closed with the owner's code, and cancelled if the part is returned; a referred buyer is never charged above the listed price (`referralPriceOk`); monthly statements for both sides (`shopStatement` / `garageStatement`) are settled outside the app. Trade agreements (`tradeDiscount`) take an agreed % off a garage's quotes. **Simulations:** the owner app plays the shops (`MartContext`, from the shared stock), the parts app plays customers, the open wall and buyers reserving / arriving (`ShopContext`), and the garage app plays the owner buying a recommended part after approving it (`PartsContext`); change them together. **OnMart promotions:** the owner's OnMart landing page (banners, offer tiles, deals, shop rows) is driven by `marketplace/deals.ts` (`dealPrice`, `validateDeal`: 1–50% off, at most 14 days; `organicRows`, `featuredShops`) and `constants/martPromos.ts`. Banners and the Featured row are paid placements (`SPONSORED_SHOP_IDS`): always labelled "දැන්වීම", and they never change the organic rows or any ranking (`deals.test.cjs`). A running deal's price reaches offers (`dealFor`). In the parts app a shop sets a deal per stock item (`DealSheet`), free delivery and a banner request that is reviewed first (`PromoSheet`); those stay local to the shop app until a backend exists.

**Far jobs (travel fee):** a job farther than `FAR_JOB_KM` (10 km, `marketplace/travel.ts`) from a garage is a "far job": the garage's `BidSheet` warns, prefills a travel compensation (`travelFeeFor`: `TRAVEL_FEE_PER_KM` beyond the free radius, `TRAVEL_FEE_MIN`) the garage may change, and sends one total bid. `Bid.price` / `MyBid.price` is that total; `travelFee` is the part of it that is travel (`bidWork(bid)` = the work alone), and a bid that has one is shown to the owner in a special way (🚗 price pill, an amber note with the breakdown in `BidsScreen`, a chip in `GarageReviewsSheet`). A win is decided on the work price only (`bidWins` ignores the travel fee). The owner simulation (`BidsContext`) has a far garage (Speed Works, 18.6 km) that bids late, and the brake job `job-seed-2` starts with its bid; the garage feed seed has a far Matara job (`FEED_POOL[5]`).

**Owner cancels a job (a three-step request):** until handover (`canRequestCancel`: booked, received, diagnosing, awaitingApproval, repairing, no request open yet) the owner can ask to cancel from the tracker or the job's chat (`CancelJobSheet`: a reason from `OWNER_CANCEL_REASONS` and a note). That is `WorkshopProgress.cancelRequest` (`CancelRequest`, status `requested`) and the work goes on hold (`WorkshopContext.patch` ignores changes while a request is open). The garage approves it and states its compensation for the work done so far (`CancelQuoteSheet` in the garage app, prefilled by `cancelCompensationFor`; `GarageContext.quoteCancel`; status `quoted`, with `compensation` and `workDone`; shown by `CancelRequestNote` on the Schedule card and in the job's chat). Then the owner decides (`CancelRequestSheet`, or the chat card): accept it (`confirmCancel`: `WorkshopProgress.cancelled`, the compensation is paid to the garage outside the app, optional ★ rating of the garage) or withdraw the request (`withdrawCancel`) and the work carries on. `workshopUpdateTexts` writes every step into the chat. The owner simulation has the garage answer 7 s after the request; the garage simulation has the owner accept a compensation up to 60% of the price after 8 s and otherwise withdraw. A cancelled job leaves the owner's Activity lists for the "අවසන්" tab; the garage app's `Booking.status` has a fourth value `'cancelled'` (+ `Booking.cancelled`, with the compensation): the Schedule tab has an "අවලංගු" chip, and every list that means "work still to do" must exclude cancelled bookings. Seeds: garage booking `b5` has an open request to answer and `b7` is already cancelled. The two apps are not linked until there is a backend, so a request made in the owner app does not reach the garage app yet.

**The whole job from the chat:** every step of a job can be done from its OnChat window, on both ends. Garage (`ChatJobActions`): vehicle received, diagnosis, extra work, a phone answer, hand over (the report and bill), close with the owner's code (`CloseJobSheet`), rework a reported problem. Owner (`ChatJobCards`): confirm the hand-over of the vehicle, approve / decline the diagnosis, extra work and Recon, show the close code or report a problem, then the receipt, a warranty claim, rating the garage (quick ★ or the full `RatingSheet`) and cancelling. A new step in the job means a new chat action or card on the side that has to do it.

**Parts Fitting, shop tags and fit requests:** category `'15'` ("Parts Fitting", `marketplace/fitting.ts`) is a job where the owner has (or bought in OnMart: the order card's "සවි කිරීමට ගරාජයක් සොයන්න", `utils/fittingBridge`) a part and asks a garage to fit it (`PartsFitting`: the part, and whether the owner brings it or the garage supplies it); it can be posted for bids (`PostJobScreen`) or booked directly (`DirectBookingSheet`), and the garage sees the part as a chip (`fittingLabel`) on its job cards and in `BidSheet`. While any job runs the owner can also ask for another part to be fitted (`FitPartSheet`: the chat's row above the replies and the tracker link on the Activity cards): `WorkshopProgress.fitRequests` (`PartFitRequest`), answered by the garage (`FitRequestNote` in `BookingActions` and the job chat: accept, or decline with a `FIT_DECLINE_REASONS` reason; `GarageContext.respondFit`) and written into both chats by `workshopUpdateTexts`. In the owner and garage chats `@` offers the parts shops (`ChatSheet` `shopTagging`: the "@" chip leads the ready-made replies; the message carries `ChatMessage.shops`, and tapping the mention or its chip opens that shop in OnMart through `utils/martBridge` `openShopFor`); a part named in a report message gets an OnMart chip (`martPartOf` / `onOpenMart`). **Consistency rules:** a cancelled booking (`status 'cancelled'`) must be left out of every "work to do" count, capacity (`intakeOn`), month totals and the trust score's accepted jobs, its compensation counts as earnings, and no workshop step is offered for it; while a cancellation request is open the job is **on hold** (`jobOnHold` in `marketplace/cancel.ts`): the garage app (`BookingActions`, `ChatJobActions`, `FitRequestNote`, Parts requests / `toOrderFor`, the add-a-detail button, technician assignment), the technician app (`ChatJobActions`, `WorkshopJobSheet`) and the owner app (approval cards, `canRequestFit`, parts to buy, the owner simulation's own steps) offer no job process, and when the owner withdraws the request everything is offered again and the owner simulation carries on from the stage the job was at (`resumeRef` in `WorkshopContext`); a far job's `travelFee` shows wherever the price does (bid cards, Schedule card, chat job record, detail view). An update line is changed only in the form it came from (`ChatSheet` `editFormFor` / `onEditReport`), never in the typing box; the cards a chat shows for what the other side waits for are anchored under the latest update line.

**SOS nudges (garage and technician apps):** `BottomNav` items take `alert` = 'incoming' (red strobe), 'approval' (fast red / amber strobe with a shake: critical, waiting for the user now), 'enroute' (blue radar), 'waiting' (slow amber) or 'active' (calm green). The garage's SOS tab shows, in that priority, a technician's pending repair-charge approval, new requests while online, a technician on the move, a running job; the technician's Jobs tab shows offers, waiting for the garage's approval, on the way, running. A pending approval also puts the shared `UrgentBar` on every screen (`SosApprovalBanner` in the garage app: approve, keep to the estimate or open the job from anywhere, `GarageContext.approveRepairPriceFor`, a phone buzz every 12 s, the waiting time; `ApprovalWaitingBar` in the technician app: the same wait with a call-the-garage button) until it is answered.

**Payment record (step 1 of the unpaid-balance plan):** closing a job with the owner's code means handed over, not paid. Right after it the garage (and the technician, for a job it closes) answers the shared `PaymentReceivedSheet` (`GarageContext.payPromptId` / `recordPayment`, `PaymentPrompt` in the garage and technician apps): the amount actually received (full by default); a shortfall needs a promised date (`PROMISE_PRESETS`, at most `MAX_PROMISE_DAYS`). It is stored as `WorkshopProgress.payment` (`JobPayment`: total, received, balance, `promisedAt`, `confirm` pending / confirmed / disputed), built by `makePayment` (`marketplace/payment.ts`), written into both chats by `workshopUpdateTexts`. The owner sees it in the tracker and the job chat (`PaymentStatus`: agree, or dispute with a note; `WorkshopContext.confirmPayment`) and on the receipt (paid / balance); the garage sees `PaymentNote` on the closed job's card, in its chat and in the detail view, which asks for the record again if the prompt was dismissed. The simulated garage in the owner app records the seeded brake job as part-paid (60%, the rest promised for tomorrow); the simulated customer in the garage app confirms a part-payment. **Following a balance up (step 2):** a part-payment is followed until it is paid. `paymentDue` (`marketplace/payment.ts`) says upcoming / today / overdue against `promisedAt`; `PaymentReminders` in both apps (a toast once a day, nothing on screen: the owner from 9:00 on the promised day and every day after; the garage from 9:00 on that day, and from 18:00 on (or any later day) asking "did it arrive?"). The garage's `PaymentNote` has "ගෙවීමක් ලැබුණා" (all or part: `collectPayment`, a new day for the rest; installments are kept), "ගෙවුවේ නැහැ" once the day has come (`markPaymentMissed`: `missedAt`, the customer is told in the chat and names a new day) and answers the customer's "I paid" claim (`answerPaymentClaim`); `ReceivablesCard` (garage Profile tab) lists what customers owe. The owner's `PaymentStatus` has "මම ගෙව්වා" (`claimPayment`), and the new-day choice after a missed day (`reschedulePayment`); `PayablesCard` (Activity, All / Completed) lists what the owner owes. Each step is a chat line from `workshopUpdateTexts`. The owner simulation has the garage report the seeded past brake job (h2, part-paid, promised yesterday) as not received 9 s after start and confirm a claim 6 s after it; the garage simulation has the customer name a new day 3 days ahead after a missed day, and the seeded booking b4 has a balance due today. **Payment reliability and limits (step 3):** `payStanding` (`marketplace/reliability.ts`, tested in `reliability.test.cjs`) turns a customer's payment records into a badge (`PayLevel`: new / good / fair / poor, `PAY_LEVEL_TEXT`) and a limit: a balance `OVERDUE_LIMIT_DAYS` (7) days past its promised day, or any overdue balance once the customer owes `OWED_LIMIT` (10,000), is `limited`; a balance due today or overdue is a `warn`; disputed balances do not count; paying it lifts the limit at once. In the owner app (`usePayStanding`, `PayStandingViews`) the Account tab shows the badge and the rule (`PayReliabilityCard`), a bar above the tab bar reminds of a due / late balance (`PayStandingBanner`), and while `limited` posting a job, accepting a bid and booking directly open `PayFirstSheet` (pay first) instead of starting; SOS, OnChat, OnMart and paying are never limited. **Garages rate customers (step 4):** after a job closed with the owner's code the garage rates the customer once (`CustomerRatingSheet` / `CustomerRatingNote` next to `PaymentNote` on the job card, in the detail view and in the chat; `GarageContext.rateCustomer`): stars, fixed reasons (`CUSTOMER_TAGS`, not free accusations), a short note moderated like a review (`NOTE_BLOCKED`); stored as `WorkshopProgress.customerRating` (`CustomerRating`), written into both chats. Rules in `marketplace/customerRating.ts` (tested in `customerRating.test.cjs`): only a closed job (`canRateCustomer`), a rating counts for `RATING_EXPIRY_MONTHS` (12) and not while the customer's dispute is open (`ratingCounts`), paying the balance turns "did not pay" into "paid late" (`settleCustomerRating`), and `summarizeCustomer` makes the `CustomerRecord` (the worse of the payment standing and the average stars, counts, the top reasons) that other garages see as `CustomerBadge` (a tappable chip on the job feed cards, direct requests, `BidSheet`, `DirectReplySheet` and the job detail view; garages' names are never shown; a customer with no history shows nothing; the garage app's `CUSTOMER_HISTORY` seeds some by phone). The owner sees what garages said on the Account tab (`PayReliabilityCard`, `useCustomerRecord`) and in the job's tracker (`CustomerRatingView`): reply to it, or dispute it (`WorkshopContext.replyToCustomerRating` / `disputeCustomerRating`; it stays out of the public record until OnGarage settles it, which waits for the admin app). The owner simulation has the garage rate the customer 9 s after closing (★5 paid in full, ★3 part-paid), and the seeded past jobs h1 (★5) and h2 (★2, unpaid) carry ratings. Next step of the plan: disputes, the admin hand-off, tests and e2e; SOS jobs have their own payment stage and are not covered yet. Money never moves through the app.

**Inquiries before booking:** a garage's card in the owner app (`GarageReviewsSheet`, opened from a service category's list, Home or a bid) has "OnChat", "❓ විමසීම" and "📅 වෙන් කරන්න". It opens the chat with that garage (`ChatTarget.profile 'garage'`, listed under the inbox's "විමසීම්" filter, `InboxThread.kind 'inquiry'`); the bar above the typing box has "❓ විමසීමක් යවන්න" (`InquirySheet`: the service, sub-service, vehicle, the question, photos; written into the chat with `inquiryText`, `marketplace/inquiry.ts`) and "📅 වෙන් කරන්න" (`GarageInquiryActions`), which closes the chat and opens the `DirectBookingSheet` for that garage on the same service, starting from what was asked (`utils/bookingBridge`, `DirectBookingSheet.initial`; a long-overdue balance still stops it, `PayFirstSheet`). In the garage app (`GarageContext.inquiries`, `GarageInquiry`, `INQUIRIES` seed + one that arrives 24 s after start) each inquiry is a chat in OnChat (`inq:` threads, `ChatKind 'inquiry'`) that opens with the customer's question and has ready answers (`INQUIRY_REPLIES`); the booking that follows arrives as a normal direct request. The two apps are not linked until there is a backend.

**Parts basket (step 1):** several parts can be asked of OnMart together. `MartContext.createBatch(inputs, title)` (owner and garage copies) makes one request per part, all with the same `PartEnquiry.batchId` / `batchTitle` (a toast once, `NewEnquiry.silent`), at most `MAX_BASKET_PARTS` (10); the shops still answer part by part. `marketplace/partsBatch.ts` (`groupByBatch`, `basketProgress`, tested in `partsBatch.test.cjs`) reads them as a group: "My requests" shows a basket as `RequestCard` (how many parts have an answer, each part's own `EnquiryCard` under it). A service kit's "ask all" is a basket. In the owner app the parts a garage told the owner to buy (`source 'owner'`) can all be asked at once from `BasketSheet` (tick the parts, who sees it; `useBasketParts` leaves out parts already bought or asked): `useChat().openBasket(workshopId)` from the tracker link, `JobPartsToBuy`'s per-job button, the approval card in the chat, and the report message's OnMart chip ("Part +N"). **Comparing a basket (step 2):** `RequestCard` shows `BatchCompare` (owner and garage copies): `shopCoverage` (`marketplace/partsBatch.ts`, tested) ranks the shops that answered by how much of the basket they have (complete first, then most parts, then cheapest; parts they said none to or will check are not covered), each with what is missing and a tap to ask that shop for the rest (`askShops` per missing part; a shop opens through `openShopFor`), and `cheapestMix` / `mixSavings` give the cheapest part-by-part buy from different shops and what it saves against the best single shop that has everything. **Technician rule:** garages assign SOS and workshop jobs to technicians (shared `TechAssignment` contract). A `TeamMember` with `hasApp` runs the SOS field steps in `apps/tech` and the garage's dispatch screen becomes a live view (`Dispatch.techMode`); a repair charge above the quote needs the manager (`priceApproval`); "take over manually" covers technicians without the app. A technician is checked in to one garage at a time and a break removes them from that garage's SOS capacity, so a freelancer is never counted twice. The owner's bill belongs to the garage; the technician earns the garage's per-job rate and nets cash collected against it. Keep the garage app's technician simulation (`runTechSim` in `GarageContext`) and `TechContext` consistent.

**Ratings and Recon (owner side):** only jobs closed with the owner's code can be rated; owners rate the garage on the four `RATING_DIMENSIONS` (they feed the trust score) and the technician separately, and the garage can reply publicly (`GarageReview`). Garages carry a `level` (`LevelBadge`) on cards and bids; a bid takes its rating, review count and level from the garage's profile. Recon for a Genuine request is the owner's decision (`ReconRequest` on `WorkshopProgress`); handover waits while one is pending (`pendingRecon`).

**Trust score and levels (garage and technician side):** the garage app computes its `TrustScore` with `computeTrustScore` from `TRUST_HISTORY` (mock of what a backend keeps) plus live reviews (with `dimensions`), completed bookings and disputes (a booking whose owner reported a problem); the level comes from `currentLevel`, and `effectiveLevel` keeps a held level through a `DEMOTION_GRACE_DAYS` grace period with a warning. Features are switched on by level (`has(feature)` in `GarageContext`; e.g. jobs where `isHighValueJob` need `highValueJobs`); locked ones stay visible on the ladder (`LevelSheet`, `FEATURE_INFO`). Levels can't be bought; Premier is by invitation with a subscription. The technician app shows the same ladder from the technician's record. In the simulation the battery booking's reported problem pushes TOPCODE's dispute rate over the trusted limit, which starts the grace period.

**Fair share, plans and the Guarantee:** monitoring (`fairnessFlags`, `FAIRNESS_SEED` in the garage app) flags a garage that takes too large a share of local work or earns over the threshold; after a 30-day notice its *new work per day* is limited by value (`computeIntake`, counted per scheduled day; base + extra mechanics; jobs under the low-value threshold and every SOS are exempt). A bid is checked against tomorrow (where a won bid is booked); a direct booking over its day's limit is never refused — `answerDirect` proposes the first day with room (`firstDayWithRoom`). Newer high-score garages see fresh bid jobs `RISING_HEAD_START_MIN` minutes first. Subscriptions are priced by earnings band (`planFor`), with a value guarantee (`valueGuarantee`: won work below 5× the fee credits the shortfall); a plan raises a limited garage's room, gives ad credits / reports and is a Premier-invite requirement, but never buys a level, ranking or level feature. Jobs with a Premier garage are `protected` (`WorkshopProgress.protected`); the owner can claim the capped OnGarage Guarantee (`eligibilityOf` + `claimBlockers`, `claimSplit`: the garage pays the deductible) — the garage responds first, then OnGarage decides (simulated in the owner app until the admin app exists). Not insurance; no real money until its legal check.

**AI decisions layer:** every "smart" suggestion (job → category/urgency/parts, SOS note → breakdown, off-app payment or contact detection, complaint triage, diagnosis note → parts, review/ad moderation) goes through `getAi()` from `@ongarage/shared` and returns `{ value, confidence, source, evidence }`. Today it is the keyword `rulesProvider` (Sinhala, Singlish and English words in `src/ai/vocabulary.ts`; English words match whole words only); later the back end installs a Claude- or Laya-backed provider with `setAiProvider()`. Never call a model from an app directly, never show a suggestion below `SUGGEST_MIN_CONFIDENCE`, and treat answers as suggestions a person confirms.

**SOS money rule:** the SOS fee is the technician's *call-out fee* (OnGarage-approved travel compensation, LKR 500 + 250 per radius expansion). It is paid to the technician even when no repair is needed. It is never a platform fee. Final bill = call-out fee + repair charge settled after inspection (may be 0). Keep wording and maths consistent in both apps (`calloutFee` in the garage app, `BASE_FEE`/`SURCHARGE_STEP` in the owner app's `SOSFlowScreen`).

**SOS capacity rule:** a garage may hold at most as many committed SOS jobs (stage past `quote`) as mechanics marked present today and not on a break, so it never takes a job another garage could serve. Attendance must be confirmed each day before any SOS can be opened. The check runs in `openDispatch` and again in `sendQuote` (`computeCrew` / `sosBlockReason` in `GarageContext`). A mechanic on a job can't be marked absent or removed, and present count can't drop below committed jobs. Jobs run in parallel; a mechanic can go on their own vehicle (`vanId: 'own'`) when the vans are out.

## Tests

- **Unit tests** (`packages/shared/test/*.test.cjs`): `run.cjs` compiles the pure-logic modules (`types`, `utils`, `constants`, `ai`, `marketplace` — nothing that imports React Native) to `.test-build/` and runs them with `node --test`. Changing a marketplace rule or the AI vocabulary means updating these tests; a future Claude/Laya provider must pass `ai.test.cjs`.
- **Browser tests** (`e2e/specs/*.cjs`, helpers in `e2e/lib.cjs`): each spec is a flow in one app's web build, starting from the seed data, run with `puppeteer-core` against an installed Chrome/Edge (`ONGARAGE_BROWSER` to point at one); page errors and native alerts fail it. Specs click by `accessibilityLabel` (English, e.g. `"Order approved parts"`) or by visible Sinhala text, so keep labels stable and give new pressables a label. Check what stays on screen rather than toasts (a later notice can replace a toast). Timings follow the simulations' delays; if a simulated delay changes, adjust the spec's waits. Screenshots go to `e2e/shots/` (git-ignored). OnMart is covered by the `mart`, `referral`, `programme` and `kits` unit tests and the browser specs `13-garage-onmart`, `31-parts-customers` and `32-owner-mart`.

## Rules that span the repo

- **Put code in `packages/shared` only if more than one app needs it.** Screens, mock data and app-specific stores stay in their app. Import shared code as `@ongarage/shared` (one barrel, `src/index.ts`); the package ships TypeScript source, Metro compiles it.
- **Theming**: never hardcode surface/text colours. Use `Colors.*` and wrap every `StyleSheet.create` in `themedStyles(() => …)` so it is rebuilt per theme. `Colors` is a proxy over the active palette; `ThemeProvider` switches it and re-renders the tree. Values that must read the palette outside a style factory (e.g. `glassStyle()`) are functions, not constants. Light/dark palettes live in `packages/shared/src/theme/colors.ts`. White text on fixed-colour gradients/pins is the intended exception.
- **Garage app home:** the Jobs tab is the first tab and the screen the app opens on (with the greeting `GarageHeader`); SOS is the second tab with a title band.
- **Shared UI behaviours:** the shared `Sheet` closes by swiping down (a `PanResponder` that only takes a downward drag while the body is scrolled to the top; on the web the handle / header and the photo carousel use `touchAction` so a phone browser does not steal the gesture; full-screen sheets are exempt). `BottomNav` items take `alert`: a flashing red emergency-light effect while the item has a badge (the garage SOS tab). `ChatIconButton` takes `size`. Every OnMart tab (owner, garage) opens on its Shops section: leaving it through the middle garage button resets the segment.
- **Look and feel** (all four apps, PickMe-inspired): soft surfaces, not outlines. Cards use `softCard()` (or `softEdge()` + `softShadow()`: a shadow on light, a faint outline only on dark), chips and secondary buttons `softFill()`, buttons are pills (`ActionButton` defaults to `pill`), icons sit on round discs (`GlassIcon`), active tab pills are `NAVY`. Each app's header is the sky-blue `headerBand()` with the tab's screen overlapping it on rounded corners; SOS flows put the map full-bleed on top with floating controls and the step in a rounded bottom sheet. These helpers live in `packages/shared/src/ui/Glass.tsx`.
- **UI language** is Sinhala (Noto Sans Sinhala via `FONTS`); English only for proper nouns and category names. Never use `Alert.alert` — tell the user with a toast (`notify()`) or a real flow.
- **Google Maps**: each app reads `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY` from its own `.env` (git-ignored; see `.env.example`). Maps render as Static Maps images with overlays projected by `projectToMap`; the Google Cloud project currently has billing disabled, so maps fall back to a dot grid.

## Photos (real camera and gallery)

Every place that attaches a photo calls `pickPhotos(max)` from `packages/shared/src/utils/photos.ts` (built on `expo-image-picker`, installed in all four apps and declared as a shared peer dependency): on a phone an alert offers Camera or Gallery, the system asks for the camera / photo permission the first time (a refusal explains how to allow it in Settings), and the local URIs come back; on the web the browser's file chooser opens (a phone browser offers its camera). The chat camera button, `MediaAttachments` (post a job, direct booking, OnMart request), the check-in / diagnosis / handover sheets, the job card updates, the parts request, the problem / warranty / guarantee sheets, the shop thread and the profile photo all use it; the old `samplePhotos` props and sample-photo auto-inserts are gone (seed data in `mockData` / `WallContext` / `WorkshopContext`, and the simulated garage's own check-in photos in the owner app, remain demo data). Each app's `app.json` has the `expo-image-picker` plugin with the camera and photo-library permission texts, so the installed app asks the device. Browser tests (`e2e/lib.cjs`) set `globalThis.__ONGARAGE_TEST_PHOTOS__` so the helper returns fixed images instead of opening a dialog; nothing in the app sets it. Photos stay as local URIs until there is a backend to upload them to.
