# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## OnGarage monorepo

Four Expo (SDK 57, React Native 0.86, React 19.2, TypeScript) apps that are the sides of one marketplace, plus the code they share. npm workspaces; one `node_modules` and one `package-lock.json` at the root.

```
apps/user       vehicle-owner app (SOS, post repair jobs, receive bids, direct bookings, workshop jobs, activity, OnMart parts marketplace, profile)
apps/garage     garage-owner app (SOS inbox + 10-step dispatch, job feed + bidding, schedule/workshop jobs, OnMart (marketplace, job parts, referrals), garage profile)
apps/parts      OnMart Shop, the parts shop's back office (garage requests + customer enquiries + open wall, orders + dispatch / counter pickup, stock, referrals, shop profile)
apps/tech       technician app (duty check-in, SOS field steps, workshop job cards, parts pickups, garages + rates, earnings)
packages/shared @ongarage/shared — types (the backend contract), theme engine + palettes, fonts, glass UI kit, line icons,
                BottomNav, Sheet, NoticeToast, SwipeCard, GarageCard, LevelBadge, CloseCode, workshop sheets, GoogleMap +
                maps helpers, service categories, formatting, marketplace rules (src/marketplace) and the AI decisions
                layer (src/ai); unit tests in test/
e2e/            browser tests for all four apps (specs/), run against the dev servers
```

There is no backend yet: every app runs on seed data and **simulates the other apps** (see below). The types in `packages/shared/src/types.ts` are meant to become the backend contract. Planned next: an admin app for OnGarage staff, then the backend, a Claude-backed AI provider, and Laya.

## Commands (run from the repo root)

```bash
npm install            # installs every workspace
npm run user           # owner app dev server,      port 8091 (npm run user:web for web)
npm run garage         # garage app dev server,     port 8092 (npm run garage:web)
npm run parts          # parts shop app dev server, port 8093 (npm run parts:web)
npm run tech           # technician app dev server, port 8094 (npm run tech:web)
npm run typecheck      # tsc --noEmit in every workspace (there is no linter; this is the check)
npm test                                        # unit tests: shared rules + AI layer
npm test -- workshop                            # only test files whose name contains "workshop"
npm test -- --test-name-pattern="grace period"  # only matching tests
npm run e2e            # browser tests against the four running dev servers
npm run e2e -- owner   # only specs whose file name contains "owner"
```

Each app's port is fixed in its `package.json` scripts, so all four run at once with no extra flags; keep ports unique when adding an app. Add a dependency to one app with `npm install <pkg> -w @ongarage/user` (keep versions identical across apps so React/React Native are hoisted once). Clear Metro's cache with `-- --clear` after moving files between packages. Installing packages can stop a running Metro server — restart it before `npm run e2e`.

## How each app is built

- **No navigation library.** `src/app/_layout.tsx` (Expo Router) just renders `src/App.tsx`, which holds the bottom-tab state (`BottomNav` from shared, tabs in `src/constants/tabs.ts`) and opens full-screen flows as `<Modal>`s. Details views and forms are sheets (the shared `Sheet`) or cross-dissolve modals.
- **Stores are React contexts in `src/context`** (owner: `BidsContext`, `BookingsContext`, `WorkshopContext`, `NoticeContext`, …; garage: `GarageContext` + `PartsContext`; parts: `ShopContext`; tech: `TechContext`). They hold the seed data from `src/constants/mockData.ts` and simulate the other sides with timers: a `live` ref gives callbacks the latest state, `later(fn, ms)` schedules a simulated reply (cleared on unmount), and `notify()` shows a `NoticeToast`. Each app wraps the shared `Sheet` and `NoticeToast` in its own `components/Sheet.tsx` / `components/Toast.tsx` so toasts appear above open sheets and modals.
- **Seed data is shared by name across apps** so the simulations line up: the garage app is "TOPCODE Tuning & Service", the parts app is shop "Galle Auto Parts" (ps1), the technician app's user is "කසුන් ජයසිංහ" (garage `TEAM` m2). Refer to seeded entities by id, never by array position. `apps/user/CLAUDE.md` has owner-app specifics.

## Marketplace flows and rules

Every owner flow has a garage counterpart: SOS request → accept/quote → assign mechanic + live location → arrived → repairing → complete → scan the owner's QR; posted job → bid (price, warranty, est. time) → booking (a bid wins in the simulation when it is ≤ 1.05 × `marketPrice`); direct booking from a service category → garage confirms the slot, proposes another time or declines within 2 h (doorstep: garage goes to the owner; otherwise the owner gets the garage's location and phone); garage profile = the `GarageCard` owners see. When changing a flow, change both sides' simulations so they stay consistent.

**Marketplace rules** live in `packages/shared/src/marketplace` so every app computes trust scores, levels, intake limits, plans, guarantee splits and workshop bills the same way; change them there (and their tests), not in an app.

**Workshop job rule:** every booked repair (won bid or confirmed direct booking) follows the shared `WorkshopProgress` (`marketplace/workshop.ts`): booked → vehicle received with condition photos → diagnosis report (findings, photos, part and labour lines) → the owner approves all, some or none of the lines → repairing → ready for handover (checklist, before/after photos, old parts kept, bill) → closed only with the owner's QR or 6-digit code (`CloseCode` / `CloseJobSheet`) → warranty. Work found mid-repair goes to the owner as an `ExtraWorkRequest` (`DiagnosisSheet` with `extra`); the owner approves it line by line (`decideExtra` in the owner app) and handover waits until they answer (`pendingExtra`). Technician diagnoses go straight to the owner — no manager review (most Sri Lankan workshops have no separate manager). Labour (agreed price + approved labour lines) and parts are billed separately (`workshopBill`). Stopping at the diagnosis costs only `INSPECTION_FEE`. A problem at handover goes to the garage for rework first, then can be escalated to OnGarage; a warranty claim is answered by the garage. The four sheets (`CheckInSheet`, `DiagnosisSheet`, `HandoverSheet`, `CloseJobSheet`) are shared by the garage app (`BookingActions`, `WorkshopPanel`) and the technician app (`WorkshopJobSheet`); the owner side is `WorkshopContext` + `components/workshop` in `apps/user`. Simulations: the garage and technician apps have the owner approve every line after a few seconds; the garage app's battery booking comes back once with a problem; the owner app simulates the garage receiving, diagnosing, asking for extra work once on the seeded brake job, reworking and scanning. Part prices come from the shared `partMarketPrice` table that the garage, technician and parts shop apps all use.

**Spare parts rule:** a garage orders parts for a booked job from nearby parts shops (Parts tab, `PartsContext`; contract types `PartsRequest` / `PartQuote` / `PartsOrder`). Shops may only quote the part type the owner chose; when the owner chose Genuine and none is available, Recon needs the owner's approval first. Parts are billed to the owner separately from the garage's labour (`Booking.partsCost`). **When:** for a workshop job, parts are ordered only for lines the owner approved (diagnosis or extra work), or before the diagnosis only for parts the owner named in their post (AI `classifyJob` → `partsMentioned`); `PartsContext.toOrderFor` gives exactly those lines, the request records them in `forLineIds`, and handover is blocked while approved parts are unordered or undelivered. **Pickup:** every quote may carry `pickup` (counter collection, parts price only); the garage chooses delivery or pickup and who collects (the garage, or a team member — one with the technician app gets a `PartsCollectTask`). A pickup order goes confirming → ready (held at the counter with a 6-digit `pickupCode`, QR payload `pickupCodePayload`) → collected; the shop checks the code with the shared `CloseJobSheet` before handing over. In the garage app `PartsContext` simulates the shops (`constants/parts.ts`); `apps/parts` (`ShopContext`) uses the same types. TOPCODE's brake-pad order is collected from the counter by its technician in both the parts app and the technician app.

**OnMart rule (spare-parts marketplace):** one marketplace across the owner app (OnMart tab), the garage app (OnMart tab: Mart / Job parts / Referrals; the old Parts tab is now "Job parts") and the parts app ("OnMart Shop", the shop's back office). Rules live in `packages/shared/src/marketplace/partsMart.ts` (search ladder `SEARCH_RINGS` 10 km, then 50 km, then nationwide; `wallVisibleTo`, `rankShops`, `shopServiceScore`, `fitmentLevel`, `priceTag`, `canonicalPartName`) and `referral.ts`; the shop directory, published stock, trade agreements and service kits are `constants/martShops.ts` and `serviceKits.ts` (shops are shared by id and name: ps1 = "Galle Auto Parts", the parts app's own shop). **Buyer flow:** ask nearby shops (or one shop), or post on the open wall (`MartAudience` shops / wall / both; the wall reaches only shops that sell that part type and never shows the poster's phone) → shops answer with a `ShopOffer` → reserve (the shop holds it; a 6-digit purchase code, QR payload `purchaseCodePayload`) → collect, inspect and pay at the counter, or delivery (inspect at the door) → warranty card, 7-day return, rating only for a verified purchase. Payment is never in the app. Shop rankings never use referral fees (tested). **Customer buys it:** a diagnosis or extra-work line with `source: 'owner'` (plus `partNo`, `recommendedShopIds`) is not ordered by the garage and not on its bill (`linesOwnerBuys`, `ownerPartsPending`, `workshopBill().ownerParts`); handover waits for a shop-verified purchase; the garage's recommendations become `PartReferral`s. **Referrals:** statuses only move forward (recommended, viewed, reserved, purchased, fitted); commission (the shop's %, default 3, cap `COMMISSION_CAP_PERCENT` = 5) is tracked, never added to the owner's price, disclosed to the owner (`referralDisclosure`), earned only when the part was fitted and the job closed with the owner's code, and cancelled if the part is returned; a referred buyer is never charged above the listed price (`referralPriceOk`); monthly statements for both sides (`shopStatement` / `garageStatement`) are settled outside the app. Trade agreements (`tradeDiscount`) take an agreed % off a garage's quotes. **Simulations:** the owner app plays the shops (`MartContext`, from the shared stock), the parts app plays customers, the open wall and buyers reserving / arriving (`ShopContext`), and the garage app plays the owner buying a recommended part after approving it (`PartsContext`); change them together. **OnMart promotions:** the owner's OnMart landing page (banners, offer tiles, deals, shop rows) is driven by `marketplace/deals.ts` (`dealPrice`, `validateDeal`: 1–50% off, at most 14 days; `organicRows`, `featuredShops`) and `constants/martPromos.ts`. Banners and the Featured row are paid placements (`SPONSORED_SHOP_IDS`): always labelled "දැන්වීම", and they never change the organic rows or any ranking (`deals.test.cjs`). A running deal's price reaches offers (`dealFor`). In the parts app a shop sets a deal per stock item (`DealSheet`), free delivery and a banner request that is reviewed first (`PromoSheet`); those stay local to the shop app until a backend exists.

**Technician rule:** garages assign SOS and workshop jobs to technicians (shared `TechAssignment` contract). A `TeamMember` with `hasApp` runs the SOS field steps in `apps/tech` and the garage's dispatch screen becomes a live view (`Dispatch.techMode`); a repair charge above the quote needs the manager (`priceApproval`); "take over manually" covers technicians without the app. A technician is checked in to one garage at a time and a break removes them from that garage's SOS capacity, so a freelancer is never counted twice. The owner's bill belongs to the garage; the technician earns the garage's per-job rate and nets cash collected against it. Keep the garage app's technician simulation (`runTechSim` in `GarageContext`) and `TechContext` consistent.

**Ratings and Recon (owner side):** only jobs closed with the owner's code can be rated; owners rate the garage on the four `RATING_DIMENSIONS` (they feed the trust score) and the technician separately, and the garage can reply publicly (`GarageReview`). Garages carry a `level` (`LevelBadge`) on cards and bids; a bid takes its rating, review count and level from the garage's profile. Recon for a Genuine request is the owner's decision (`ReconRequest` on `WorkshopProgress`); handover waits while one is pending (`pendingRecon`).

**Trust score and levels (garage and technician side):** the garage app computes its `TrustScore` with `computeTrustScore` from `TRUST_HISTORY` (mock of what a backend keeps) plus live reviews (with `dimensions`), completed bookings and disputes (a booking whose owner reported a problem); the level comes from `currentLevel`, and `effectiveLevel` keeps a held level through a `DEMOTION_GRACE_DAYS` grace period with a warning. Features are switched on by level (`has(feature)` in `GarageContext`; e.g. jobs where `isHighValueJob` need `highValueJobs`); locked ones stay visible on the ladder (`LevelSheet`, `FEATURE_INFO`). Levels can't be bought; Premier is by invitation with a subscription. The technician app shows the same ladder from the technician's record. In the simulation the battery booking's reported problem pushes TOPCODE's dispute rate over the trusted limit, which starts the grace period.

**Fair share, plans and the Guarantee:** monitoring (`fairnessFlags`, `FAIRNESS_SEED` in the garage app) flags a garage that takes too large a share of local work or earns over the threshold; after a 30-day notice its *new work per day* is limited by value (`computeIntake`, counted per scheduled day; base + extra mechanics; jobs under the low-value threshold and every SOS are exempt). A bid is checked against tomorrow (where a won bid is booked); a direct booking over its day's limit is never refused — `answerDirect` proposes the first day with room (`firstDayWithRoom`). Newer high-score garages see fresh bid jobs `RISING_HEAD_START_MIN` minutes first. Subscriptions are priced by earnings band (`planFor`), with a value guarantee (`valueGuarantee`: won work below 5× the fee credits the shortfall); a plan raises a limited garage's room, gives ad credits / reports and is a Premier-invite requirement, but never buys a level, ranking or level feature. Jobs with a Premier garage are `protected` (`WorkshopProgress.protected`); the owner can claim the capped OnGarage Guarantee (`eligibilityOf` + `claimBlockers`, `claimSplit`: the garage pays the deductible) — the garage responds first, then OnGarage decides (simulated in the owner app until the admin app exists). Not insurance; no real money until its legal check.

**AI decisions layer:** every "smart" suggestion (job → category/urgency/parts, SOS note → breakdown, off-app payment or contact detection, complaint triage, diagnosis note → parts, review/ad moderation) goes through `getAi()` from `@ongarage/shared` and returns `{ value, confidence, source, evidence }`. Today it is the keyword `rulesProvider` (Sinhala, Singlish and English words in `src/ai/vocabulary.ts`; English words match whole words only); later the back end installs a Claude- or Laya-backed provider with `setAiProvider()`. Never call a model from an app directly, never show a suggestion below `SUGGEST_MIN_CONFIDENCE`, and treat answers as suggestions a person confirms.

**SOS money rule:** the SOS fee is the technician's *call-out fee* (OnGarage-approved travel compensation, LKR 500 + 250 per radius expansion). It is paid to the technician even when no repair is needed. It is never a platform fee. Final bill = call-out fee + repair charge settled after inspection (may be 0). Keep wording and maths consistent in both apps (`calloutFee` in the garage app, `BASE_FEE`/`SURCHARGE_STEP` in the owner app's `SOSFlowScreen`).

**SOS capacity rule:** a garage may hold at most as many committed SOS jobs (stage past `quote`) as mechanics marked present today and not on a break, so it never takes a job another garage could serve. Attendance must be confirmed each day before any SOS can be opened. The check runs in `openDispatch` and again in `sendQuote` (`computeCrew` / `sosBlockReason` in `GarageContext`). A mechanic on a job can't be marked absent or removed, and present count can't drop below committed jobs. Jobs run in parallel; a mechanic can go on their own vehicle (`vanId: 'own'`) when the vans are out.

## Tests

- **Unit tests** (`packages/shared/test/*.test.cjs`): `run.cjs` compiles the pure-logic modules (`types`, `utils`, `constants`, `ai`, `marketplace` — nothing that imports React Native) to `.test-build/` and runs them with `node --test`. Changing a marketplace rule or the AI vocabulary means updating these tests; a future Claude/Laya provider must pass `ai.test.cjs`.
- **Browser tests** (`e2e/specs/*.cjs`, helpers in `e2e/lib.cjs`): each spec is a flow in one app's web build, starting from the seed data, run with `puppeteer-core` against an installed Chrome/Edge (`ONGARAGE_BROWSER` to point at one); page errors and native alerts fail it. Specs click by `accessibilityLabel` (English, e.g. `"Order approved parts"`) or by visible Sinhala text, so keep labels stable and give new pressables a label. Check what stays on screen rather than toasts (a later notice can replace a toast). Timings follow the simulations' delays; if a simulated delay changes, adjust the spec's waits. Screenshots go to `e2e/shots/` (git-ignored). OnMart is covered by the `mart`, `referral`, `programme` and `kits` unit tests and the browser specs `13-garage-onmart`, `31-parts-customers` and `32-owner-mart`.

## Rules that span the repo

- **Put code in `packages/shared` only if more than one app needs it.** Screens, mock data and app-specific stores stay in their app. Import shared code as `@ongarage/shared` (one barrel, `src/index.ts`); the package ships TypeScript source, Metro compiles it.
- **Theming**: never hardcode surface/text colours. Use `Colors.*` and wrap every `StyleSheet.create` in `themedStyles(() => …)` so it is rebuilt per theme. `Colors` is a proxy over the active palette; `ThemeProvider` switches it and re-renders the tree. Values that must read the palette outside a style factory (e.g. `glassStyle()`) are functions, not constants. Light/dark palettes live in `packages/shared/src/theme/colors.ts`. White text on fixed-colour gradients/pins is the intended exception.
- **Look and feel** (all four apps, PickMe-inspired): soft surfaces, not outlines. Cards use `softCard()` (or `softEdge()` + `softShadow()`: a shadow on light, a faint outline only on dark), chips and secondary buttons `softFill()`, buttons are pills (`ActionButton` defaults to `pill`), icons sit on round discs (`GlassIcon`), active tab pills are `NAVY`. Each app's header is the sky-blue `headerBand()` with the tab's screen overlapping it on rounded corners; SOS flows put the map full-bleed on top with floating controls and the step in a rounded bottom sheet. These helpers live in `packages/shared/src/ui/Glass.tsx`.
- **UI language** is Sinhala (Noto Sans Sinhala via `FONTS`); English only for proper nouns and category names. Never use `Alert.alert` — tell the user with a toast (`notify()`) or a real flow.
- **Google Maps**: each app reads `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY` from its own `.env` (git-ignored; see `.env.example`). Maps render as Static Maps images with overlays projected by `projectToMap`; the Google Cloud project currently has billing disabled, so maps fall back to a dot grid.
